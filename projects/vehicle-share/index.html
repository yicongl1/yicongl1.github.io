团队课程项目（4 人）

车辆共享平台数据库设计（UTC-NF18）

贡比涅技术大学 · NF18 关系与非关系数据库设计（2024 春）

为 vehicleShare 车辆共享平台完成从需求澄清、UML 类图、关系模型到 PostgreSQL 落地的完整设计：18 张表、完整性约束、Python/psycopg2 命令行应用，以及用 JSON 列承载保险、发票与评论的 NoSQL 变体。

项目背景

vehicleShare 是一个“个人之间自助租车”的平台：车主发布车辆公告并设定可用时段，个人租客或企业在线预订、签署租赁合同、取还车时各做一次车况检查，最后收到一张包含租金、超里程和油量补偿的发票。价格之外，平台还要处理评分、举报、保险、可选配置和可行驶国家。

这是 UTC NF18「关系与非关系数据库设计」 的四人课程项目，2024 年春季完成。任务不是写一个能跑的增删改查，而是把整套业务从需求澄清一路做到数据库：UML 类图、关系模型（MLD）、PostgreSQL 建表与约束、Python 命令行应用、规范化分析，最后再给出一版以 JSON 列承载半结构化数据的 NoSQL 方案。

数据模型

模型可以分成四块：

  • 用户体系：母表 Utilisateur 保存登录名、密码、类型和启用状态；子表 Proprietaire、Locataire、Entreprise 保存各自属性。企业下再挂 Conducteur。
  • 车辆：Vehicule 以车牌号为主键，关联车主、保险合同、可用时段、选项和允许行驶的国家。
  • 交易链：Annonce → Contrat_location → Etat_des_lieux（取车、还车各一条）+ Facture + Commentaire。
  • 多对多关系：Est_disponible、Peut_circuler、Possede 三张关联表，用复合主键表达“车辆—时段”“车辆—国家”“车辆—选项”。

实现要点

  • 完整性约束尽量下沉到数据库。 电话格式用 CHECK (telephone LIKE '__________')，年龄 >= 18，评分 0..5，油量 0..1；合同必须二选一：CHECK ((locataire IS NOT NULL AND entreprise IS NULL) OR (locataire IS NULL AND entreprise IS NOT NULL))。
  • 业务规则也可以写成约束。 公告被举报三次必须下架，对应 CHECK (NOT(nombre_signalement >= 3 AND activite))；这条规则不依赖应用代码，任何写入路径都绕不过去。
  • Python 应用用 psycopg2 参数化查询。 登录、查重、插入和删除大多使用 %s 占位符；应用层负责菜单、权限判断和日期合法性，数据库负责结构、外键和行内一致性。
  • NoSQL 变体只改“该改的地方”。 Vehicule.contrat_assurance、Contrat_location.commentaire、Contrat_location.facture 改成 JSON 列，删掉对应的三张表；查询用 ->> 取字段，例如 WHERE Contrat_assurance->>'type' = 'Tous risques'。

结果与反思

仓库保留了五次正式交付（需求澄清、UML/MLD、SQL、Python 应用、规范化）和 NoSQL 扩展。按交付顺序读，可以看到一个数据库从“想法”变成“可查询结构”的过程。

回头看，这个项目最值得保留的不是某条 SQL，而是几个判断：

  • 哪些规则必须写进数据库，哪些更适合放在应用层；
  • 什么时候用继承表，什么时候用一张带类型字段的表；
  • JSON 列能省掉表，但也会把约束、索引和聚合查询的代价一起省掉。

源码、SQL 脚本、报告与 NoSQL 版本：https://github.com/yicongl1/Vehicle-Share-Database
