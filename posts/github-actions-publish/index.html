把发布交给 GitHub Actions：双仓库、单提交与一次跨平台迁移

  • Hugo
  • GitHub Actions
  • CI/CD
  • 自动化部署

字体

字号

100%

这个站点一直是「本地构建、本地加密、本地强推」：改完内容，跑一个 PowerShell 脚本，等一两分钟构建和加密，再把产物推上去。人必须待在电脑前，而且那台电脑得装好 Hugo、Node、Dart Sass，密码文件也得在。

内容越写越多之后，这件事开始碍事——尤其是出门在外、只想改一句话的时候。于是把整条流水线搬到了 GitHub Actions。下面是设计、踩坑和从 Windows runner 换到 Linux 的记录。

一、约束

站点有两个仓库，职责完全不同：

仓库内容谁能写
源码仓库（私有）Markdown、模板、脚本我，手工提交
站点仓库（公开）构建产物只由流水线强推

三条约束决定了方案：

  1. 源码不能进公开仓库——非公开内容在建站时就该被排除在外；
  2. 公开仓库只有一个 Site update 提交——如果保留线性历史，diff 会暴露「这次改了哪些文件、新增了哪些页面」；
  3. 非公开页面必须加密后才能上线——构建产物里它们仍是明文，加密这一步不能省。

所以流水线不是「Hugo 构建完推上去」这么简单，而是：构建 → 加密 → 压成一个提交 → 强推。

二、流水线的形状

触发条件只有两个：推送到私有仓库的 main，或者手动点一次 Run workflow。

on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          submodules: recursive
      - uses: peaceiris/actions-hugo@v3
        with:
          hugo-version: '0.169.0'
          extended: true
      # ... Node、Dart Sass、npm ci ...
      - run: bash scripts/publish.sh   # 构建 + 加密
      - run: ./scripts/check-site.ps1  # 冒烟检查
      - uses: peaceiris/actions-gh-pages@v4
        with:
          personal_token: ${{ secrets.PAGES_TOKEN }}
          external_repository: yicongl1/yicongl1.github.io
          publish_branch: main
          publish_dir: ./public
          force_orphan: true
          full_commit_message: Site update

几处细节值得写下来：

  • force_orphan: true 让目标分支每次都从零开始，历史永远只有一个提交，天然满足约束 2；
  • full_commit_message 是为了压掉这个 action 的默认行为——它会在提交信息后面拼上 仓库@提交号，把源码仓库名和 SHA 带到公开仓库里；
  • 推送到另一个仓库需要自己的令牌，GITHUB_TOKEN 只管当前仓库。所以 Secret 里放一个 fine-grained PAT，权限只给公开仓库的 Contents: Read and write。

三、两个最容易踩的坑

第一个：Secret 存在哪，令牌指向哪。

令牌是给公开仓库用的，但 Secret 必须加在私有仓库里——因为工作流跑在私有仓库。这两个位置很容易搞反。第一次配置时令牌建好了，却忘了勾选仓库和权限，结果是：构建、加密、检查全部通过，最后一步 403。

排查顺序也因此变得很直接：看红的是哪一步。如果卡在密码那步，是密码 Secret 的问题；如果卡在最后一步，几乎一定是令牌权限。

第二个：改密码要改两处。

线上生效的是 Actions Secret 里的密码；本地还留着同一份密码，供兜底发布时使用。只改 Secret 也就算了，麻烦的是反过来：某天 Actions 出问题，本地跑一次脚本，它会用旧密码重新加密并推上去，线上密码被悄悄改回旧的。

这是双通道的固有代价，没有优雅的解法，只能定一条规则：改密码时两处一起改，然后触发一次运行让新密文生效。

四、从 Windows runner 换到 Linux

第一版工作流跑在 windows-latest，理由很实在：加密脚本是 PowerShell 写的，直接复用最省事。

代价是启动慢、磁盘慢，计费还是 1 倍额度的 2 倍。真正让我下决心的是磁盘：构建要写三千多个文件，加密再把非公开页面逐页重写一遍，Windows runner 在这件事上明显吃亏。

迁移的难点不是换 runs-on，而是不能让加密逻辑分裂成两份。做法是把 PowerShell 里的逻辑抽成一个 Node 脚本——跨平台、逻辑只有一份：

// 加密脚本（节选）
const result = spawnSync(process.execPath, [
  cli, siteDir, "-r", "-d", tmpOut,
  "-p", pass, "--remember", "7", "--short", "-t", template,
], { stdio: "inherit" });

if (result.status !== 0 || !fs.existsSync(encrypted)) {
  dropPlaintext();               // 失败时删掉明文，绝不让它有机会被发布
  die("Encryption failed");
}

原来的 PowerShell 加密脚本退化成十几行的薄封装，本地 Windows 流程不变；Linux 侧新增 publish.sh，负责「清理 → 构建 → 删目录说明 → 加密」。两个平台跑的是同一份加密代码，不会因为改了一边忘了另一边而对不上。

Dart Sass 也换成官方 linux 包，版本仍然钉死，避免「今天和昨天构建结果不一样」。

五、体积优化

迁移时量了一下产物，发现两处明显的浪费：

  • 五首早就没人引用的背景音乐（13.8MB）。它们对应的页面后来改用内嵌音频，这几首一直白传。移到 assets/ 下（不参与构建），要恢复随时能改回去。
  • node_modules 每次重装约 35 秒。加一层缓存，命中就跳过 npm ci。

也试过缓存 Hugo 的 resources/（图片处理缓存），结果冷热都在 28–29 秒——说明这个站点的构建瓶颈不在图片处理，缓存它没有意义，于是没加。

最终产物从 218MB 降到 204MB；加密整站约 20–25 秒。

六、现在的边界

  • 推送即发布，不需要守着电脑；网页上改一个错别字也能触发。
  • 抓取仍然只在本地：B 站、豆瓣、LeetCode 的接口有风控，不适合每次构建都去请求，数据仍然是本地跑完再提交。
  • 加密区只保护页面本身：站点地图、搜索索引和 RSS 都不收录非公开页面，这条规则在 CI 里同样要守住。

这次迁移真正解决的问题不是「快了几分钟」，而是把「发布」从一个需要特定机器、特定环境、人在场的动作，变成了一个普通的 git push。代价是多了一个需要维护的令牌、一处需要同步的密码，以及一个失败时只能看日志的远端环境——但这些都是可以写进文档、变成规则的东西。

这个站点本身记录在个人网站项目页里，那里有它的整体结构和相关文章。
