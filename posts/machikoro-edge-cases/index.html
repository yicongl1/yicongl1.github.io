桌游程序的边界：MachiKoro 的购买流程、索引与 AI

项目代码：https://github.com/yicongl1/Machikoro

规则写对只是第一步。真正让人崩溃的是边界：买不起怎么办、卡槽编号在购买后变了、AI 选了一个不合法的动作、输入的字符串看起来对但匹配不上。

这篇记录 MachiKoro 项目里购买与输入处理的设计，以及修过的几类典型 bug。

购买流程：返回值到底表示什么

早期版本的 player_input() 返回一个 int，这个 int 有时候表示"卡槽编号"，有时候表示"剩余金币数"，还可能是 -1 表示不买。结果就是：

  • 买地标时把金币数当成下标，越界
  • slot[0] 永远买不到
  • 先扣钱、后校验，买不起也能把金币扣成负数

后来把返回值语义固定下来：

enum PurchaseCode {
    NO_PURCHASE = -1,      // 选择 no，结束购买
    YELLOW_PURCHASE = -2   // 已成功购买一张大型建筑
};

普通建筑返回真实的卡槽下标，两个特殊值负责"不买"和"已买地标"。调用方只需要判断这三种情况，不再猜数字的含义。

更好的写法是 enum class + std::optional<int>(C++17 起),避免负数和下标混在一起。但在一个 C++14 的控制台作业里,能用枚举把语义写清楚,已经比"魔法数字"好很多。

先校验，后扣钱

购买普通建筑时，所有失败条件都必须在 withdraw() 之前检查：

bool Game::buy_slot(int index) {
    if (index < 0 || index >= (int)slot.size() || slot[index].empty())
        return false;

    Card* card = slot[index].back();

    // 紫卡不能重复拥有
    if (card->get_color() == Color::purple) {
        for (PurpleCard* owned : p->purple_cards) {
            if (owned->get_name() == card->get_name())
                return false;
        }
    }

    // 钱不够
    if (p->bank->get_coins() < card->get_cost())
        return false;

    // 到这里才真正扣钱
    p->bank->withdraw(card->get_cost());
    // ...
}

这是一条很朴素的规则：任何可能失败的操作，都把失败判断放在状态修改之前。一旦顺序反了，后面每一条错误分支都要负责"把钱加回去"，很容易漏。

地标购买同理，只是它还多一个 active 状态：

if (card->active) return false;                       // 已经买过
if (p->bank->get_coins() < card->get_cost()) return false;
p->bank->withdraw(card->get_cost());
card->active = true;

卡槽索引会失效

市场是一个 vector<vector<Card*>>：每个槽位放同一种卡的多张副本。购买时从槽位尾部拿走一张：

slot[index].pop_back();
if (slot[index].empty()) slot.erase(slot.begin() + index);

问题来了：erase 之后，后面所有槽位的下标都会前移。如果界面还拿着旧的编号，下一次购买就可能买错卡，甚至越界。

处理方式不是"记住偏移量"，而是购买成功后重新打印市场，让玩家基于最新状态重新选择。同时所有边界判断都使用当前的 slot.size()，而不是缓存的数量。

if (selection < 0 || selection >= (int)slot.size()) continue;

这也是一个通用经验：索引只在它对应的容器没有变化时有效。容器一变，旧索引就应该视为失效。

AI：先保证合法，再谈聪明

AI 的目标不是打败人类，而是"能自己完整打完一局"。所以它不预测对手，只做一件事：构造一个合法动作候选集，然后随机选。

vector<string> options;

for (int i = 0; i < (int)slot.size(); i++) {
    if (slot[i].empty()) continue;
    Card* c = slot[i][0];
    if (p->bank->get_coins() < c->get_cost()) continue;

    if (c->get_color() == Color::purple) {
        bool owned = false;
        for (PurpleCard* card : p->purple_cards)
            if (card->get_name() == c->get_name()) owned = true;
        if (owned) continue;
    }

    options.push_back("acheter " + to_string(i));
}

地标也走同一套逻辑：只把"没买过且买得起"的放进候选。候选为空就输出 no，直接结束购买阶段。

AI 和人类共用 player_input() 的解析与购买流程，区别只在于字符串从哪里来：人类来自 getline()，AI 来自候选集。不要让 AI 走一条只有 AI 会走的代码路径，否则人类流程里的 bug 它永远测不出来。

输入解析：正则 + 归一化 + 单行

控制台程序最容易死在输入上。这个项目的几条约定：

  1. 统一用 getline()，不混用 cin >>。混用会把换行符留在缓冲区，下一轮读到空行。
  2. 先 normalize()：去掉首尾空白、压缩连续空格。玩家多打一个空格不应该导致命令失效。
  3. 用正则匹配整体命令，而不是逐个字符猜：
string cmds = "(no)"
    "|(voir [0-9]+)"
    "|(voir table)"
    "|(voir tableau)"
    "|(acheter [0-9]+)"
    "|(acheter TrainStation)"
    "|(acheter ShoppingMall)"
    "|(acheter AmusementPark)"
    "|(acheter RadioTower)";
regex view(cmds);
  1. 数字单独用 parse_int() 解析，失败就报错，不直接 stoi()。早期 voir table 会触发 stoi("table") 异常，就是因为把"查看市场"和"查看某个玩家"混在同一个分支里。
  2. getline() 返回 false（EOF）时正常退出，避免管道输入时无限循环。

几个"看起来能跑"的规则 bug

  • 紫卡只在点数 6 时触发：早期按卡牌上的点数区间判断，结果商业中心在别的点数也会触发。
  • 体育场不能向自己收钱：遍历玩家时忘了跳过当前玩家，金币从左口袋进右口袋。
  • 购物中心的下标是 1，不是 2：地标固定槽位写错，导致加成永远不生效。
  • 倍率要读 get_multiplier_icon()：早期直接比较卡牌颜色，奶酪工厂、家具工厂、果蔬市场的倍率恒为 0。
  • dynamic_cast 比卡名可靠：用字符串比较判断"这是不是电视台"，名字一改效果就静默消失。
  • 游乐园只在掷出对子时加回合：不是"买了就每回合多走一次"。

这些 bug 有一个共同点：代码能编译、能运行、甚至能玩，但规则是错的。桌游项目最大的测试成本不在崩溃，而在"看起来正常"。

小结

这个项目让我印象最深的不是某个设计模式，而是三件很具体的事：

  1. 返回值要有明确语义。负数、金币数、下标混在一起，迟早出事。
  2. 先校验，后修改。所有失败分支都应该发生在状态改变之前。
  3. 用类型和容器表达约束。紫卡不能重复、地标有 active、卡槽数量会变——这些都应该在代码结构里看得见，而不是靠注释提醒。
