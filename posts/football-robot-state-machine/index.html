把 15 秒的比赛规则写成状态机：Lua 战术层与 C++ 技能层

    项目仓库：https://github.com/yicongl1/iLoboke-Robot-Soccer-2022

    2022 年那场足球机器人赛，规则里最关键的一句话是：每个固定点位 15 秒内完成，射门前至少一次传接配合。它把“让机器人踢球”这道开放题，压成了一道可以被脚本穷举的流程题——两个演员、五个起点、三个状态。

    这篇拆一下当时的代码是怎么组织的：Lua 战术层、C++ 技能层，以及一个我到现在还觉得有意思的 bug。

    平台只给两层接口

    赛项平台 SOM 3.4.2 的扩展方式很克制，只有两层：

    • Team/lua_scripts/play/Package/<场景>/ 下的 Lua 战术脚本，由 Play.lua 调度；
    • Team/user_skills/<名字>.dll 下的 C++ 技能动态库，Lua 通过 task.KickerTask("名字") 直接调用。

    Play.lua 本身就是一个状态机调度器。每个战术脚本用一张表注册进去：

    gPlayTable.CreatePlay{
  name = "P_Back",
  firstState = "GetBall",
  ["GetBall"] = { switch = ..., Kicker = ..., Receiver = ... },
}

    每帧做三件事：换了 play 就重置到 firstState；调当前状态的 switch() 拿到下一个状态名（或 "finish"）；对状态里列出的每个角色执行对应的 task()。task 是闭包，最终落到 C++ 侧的 CKicker_Skill(name, posX, posY, dir, kickflat, kp, cp)——name 就是 DLL 的文件名，kp 和 cp 是平射与挑射的力度，不写就是 kp=127、cp=6。

    所以这层的写法很像游戏 AI 的行为树：状态描述“每个角色此刻该做什么”，switch 描述“什么条件下换下一组”。区别是它没有内部记忆，每帧都重新计算——所有状态都藏在机器人自己的位置和视觉反馈里。

    一个点位就是三个状态

    五个点位（后场区、中场点、前场区、角球区、点球点）共用同一副骨架：拿球 → 传球 → 射门。后场任意球的完整脚本是这样的：

    ["GetBall"] = {
switch = function()
if Cbuf_cnt((CBall2RoleDist("Receiver") < 30 and CRole2TargetDist("Kicker") < 5), 120) then
return "PassBall"
end
end,
Kicker   = task.GotoPos("Kicker", 80, 5, KickerRole2BallDir),
Receiver = task.GetBall("Receiver", "Kicker"),
},
["PassBall"] = {
switch = function()
if CIsBallKick("Receiver") or CBall2RoleDist("Receiver") < 5 or Cbuf_cnt(ture, 120) then
return "Shoot"
end
end,
Kicker   = task.RobotHalt("Kicker"),
Receiver = task.ReceiverTask("chuanqiu"),
Goalie   = task.Goalie(),
},
["Shoot"] = {
switch = function()
if CIsBallKick("Kicker") then return "finish" end
end,
Receiver = task.GotoPos("Receiver", -176, -178, 0),
Kicker   = task.KickerTask("shemen"),
Goalie   = task.Goalie(),
},

    几个值得说的点：

    • Cbuf_cnt(条件, 120) 不是“条件成立”，而是“条件连续成立 120 帧”。少一帧就重置，所以一次视觉抖动不会把流程推走；
    • 状态里三个角色必须都写：1 号守门员、3 号主罚、5 号接应。漏写一个，那一帧就没人给他下指令；
    • 射门时 5 号退到 (-176, -178) 让开射门线。这不是战术，是避免自己挡球的卫生习惯，但忘了就会白丢一个点位。

    状态机最脆弱的地方：转移条件

    写状态机的经验是，难点从来不在状态本身，而在你怎么知道可以走了。

    仿真里位置是精确的，< 30、< 5 这种阈值很好定。实地上一台机器人可能停在“差一点到位”的位置，判定条件永远不成立，整段流程就卡在这里等一个不会来的事件。

    我们的补法是加一层帧计时：Cbuf_cnt 的第二个参数既是“要连续满足多久”，也兼作超时上限——条件不满足时它返回 0，时间一到就强制往下走。原理上，这等于给每个转移加了一条 timeout → next 的边。

    于是问题来了：这条边写错了怎么办？

    if CIsBallKick("Receiver") or CBall2RoleDist("Receiver") < 5 or Cbuf_cnt(ture, 120) then

    ture 是 true 的笔误。Lua 里未定义变量是 nil，所以 Cbuf_cnt(nil, 120) 永远返回 false——这条兜底边从来没生效过。P_ 系列一共 10 处都是这个写法。

    后果很具体：只要 5 号那一脚传球踢空，状态机就卡在 PassBall 里，直到 15 秒被判满。技术报告里“传球踢空”被列成第一号难点，但当时代码里没人意识到兜底分支本身是坏的——因为仿真里传球成功率高，这条路根本没走过。

    这件事给我的教训不是“别打错字”，而是：兜底分支如果没被专门演练过，就等于没有。它只在最坏的情况下执行，而最坏的情况恰恰是没法靠“平时跑得挺顺”来验证的。

    技能层：为什么还要自己写 DLL

    Lua 只负责“什么时候做”，不负责“做得准不准”。官方内置的传球函数在仿真里够用，上实地就不稳，所以我们自己写了一组技能 DLL：传球（mypass、chuanqiu）、射门（myshoot、shemen）、拿球后朝向（myget1、Face_Getball）、点球（dianqiu）。Lua 传坐标、朝向和力度，DLL 里管的是速度矢量、出球角度和吸球动作。

    结果是个很典型的落差：这套 DLL 在仿真里把进球率从 50% 推到 90%，到实地上效果“甚微”。所以我们又写了一套完全只用官方函数的战术脚本作为兜底，现场一旦自写 DLL 不灵就整套替换。两套脚本跑同一批点位，是这个项目里性价比最高的一个决定。

    如果重来

    • 把参数赶出代码。 (80, 5)、(-176, -178)、30、5、kp=127 散在十几份脚本里，现场改一个数要翻七八个文件，最后只能写在 test.txt 里手记。
    • 让兜底路径可演练。 加一个“故意让传球失败”的开关，每次调参顺手跑一遍，兜底坏了当天就能发现。
    • 状态名和 DLL 名统一检查。 Lua 里写错一个技能名不会报错，只会静默不动——这类问题在场上极难定位。

    代码和文档都在仓库里，包括那个 ture——它被原样保留着，只在 代码导读.md 里标了出来。改了它，仓库就和当年提交的包对不上了。
