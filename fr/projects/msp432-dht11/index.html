Projet de cours · pilote et mise au point

MSP432 + DHT11 : écrire soi-même le pilote monofilaire

Université de Shanghai · Conception des systèmes embarqués (automne 2021)

Sans bibliothèque capteur — la trame de 40 bits du DHT11 est lue au GPIO et au Timer_A : impulsion de départ de 18 ms, échantillonnage à 40 µs, somme de contrôle sur 8 bits. Le code est séparé en pilote réutilisable et démonstration UART, avec la version monofichier d'origine conservée.

sept. 2021 - janv. 2022 C · MSP432 · DriverLib · UART Conception des systèmes embarqués (SHU-23286056) →

Pourquoi l’écrire à la main

Le DHT11 n’a ni SPI ni I²C : une seule ligne de données transporte 40 bits sous forme de largeurs d’impulsion. Le cours imposait une implémentation MSP432P401R + DriverLib sans bibliothèque capteur, ce qui en fait un exercice compact de GPIO, temporisation, interruption et UART.

Câblage

La plage d’alimentation va de 3,0 à 5,5 V : 3,3 V correspond à la logique du MSP432. La ligne de données est à drain ouvert ; sans tirage, elle flotte ou reste haute, ce qui explique la plupart des échecs de lecture.

Chronogramme

Une transaction comporte trois parties :

  1. Départ : le MCU tire la ligne à 0 pendant au moins 18 ms, puis la relâche.
  2. Réponse : le capteur tire à 0 pendant ~80 µs, puis à 1 pendant ~80 µs.
  3. 40 bits : chaque bit commence par ~50 µs à 0 ; la largeur du niveau haut code 0 ou 1.

Le point d’échantillonnage à 40 µs est le cœur du pilote : plus tôt, les deux bits sont hauts ; plus tard, même un 1 peut être terminé.

Structure du code

  • dht11.c : impulsion de départ, détection de réponse, read_byte() bit par bit, somme de contrôle ;
  • dht11.h : dht11_init(), dht11_read(), dht11_delay_ms() ;
  • main.c : DCO à 24 MHz, UART A0 à 115200, une mesure toutes les 2 s affichée TxxC RHxx%.

delay_us(n) utilise le Timer_A : CCR0 reçoit 24×n, le compteur démarre, et l’interruption ne fait que poser un drapeau. Pas de calibration par boucle vide ; changer l’horloge revient à changer une constante.

read_byte() attend la fin du niveau bas de 50 µs, temporise 40 µs, échantillonne, puis attend la fin du niveau haut. Un compteur guard évite l’attente infinie si le capteur disparaît.

Pièges de la version d’origine

Le code de cours tenait en un fichier. Il fonctionnait, mais :

  • time_count n’était pas volatile : le compilateur pouvait le mettre en cache et la boucle d’attente ne jamais finir ;
  • flag n’était pas initialisé : une erreur de somme de contrôle renvoyait une valeur aléatoire ;
  • delay_us et delay_ms reconfiguraient le Timer_A en boucle, et delay_ms appelait delay_us à chaque milliseconde ;
  • la boucle principale n’avait aucun chemin d’erreur : une lecture ratée n’affichait rien.

La version séparée corrige ces points : volatile, initialisation à 0, retour -1 en cas d’échec, message d’erreur dans main. Le fichier d’origine est conservé dans legacy/.

Résultats et limites

Sur une LaunchPad MSP432P401R avec un DHT11, l’UART affiche des mesures stables et la LED bascule à chaque lecture réussie. Les limites sont réelles :

  • résolution de 1 °C / 1 %HR ; une lecture par seconde au maximum ;
  • la lecture bloque environ 20 ms ; pas de DMA ni de capture d’entrée ;
  • somme de contrôle sur 8 bits, pas de CRC ;
  • fils longs, tirage absent ou alimentation instable provoquent des erreurs de somme.

La suite serait la capture d’entrée + DMA pour libérer le CPU pendant la trame de 40 bits, mais cela dépasse le cadre du cours.

Le code et le câblage sont dans le dépôt ; le récit d’implémentation est dans cet article.
