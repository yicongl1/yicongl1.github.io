静态站的语言跳转：为什么我没用 IP 定位

站点有中文、英文、法文三个版本。之前的做法是让访客自己点右上角的语言选择器；最近加了一个"首次访问自动跳转"，规则很简单： 浏览器语言是法语 → /fr/ 浏览器语言是中文 → 中文首页 其他语言 → /en/ 没有采集 IP，也没有调用任何第三方接口。 这篇记录为什么这么做，以及静态站做语言跳转时容易踩的坑。 静态站拿不到 IP 这是最先要接受的事实。GitHub Pages 这类纯静态托管只负责把文件发出去，不执行服务端代码，所以： 不能在服务器端读 X-Forwarded-For 不能根据国家做 302 不能在 HTML 返回前决定语言 想在浏览器里按国家跳转，只能调用第三方 IP 地理库： const res = await fetch("https://ipwho.is/"); const { country_code } = await res.json(); 这能工作，但代价不小： 多一次外部请求：首屏要等它返回，慢的时候会先看到中文再跳走。 隐私问题：IP 属于个人数据。站点在法国，面向欧洲访客时，把每个访客的 IP 发给第三方需要更谨慎地说明处理目的。 误判：VPN、公司出口 IP、跨境网络都会让"国家"不等于"语言"。 可用性：免费接口有限流，挂掉时只能回退。 对个人作品集来说，这些成本换来的精度并不值得。 浏览器语言是更直接的信号 访客想要什么语言，浏览器其实已经说了： navigator.language // "fr-FR" navigator.languages // ["fr-FR", "fr", "en"] 它比 IP 更接近"用户能读什么语言"，而不是"用户此刻在哪"。一个法国人在德国出差，浏览器仍然是 fr-FR；一个在法国的英语使用者，浏览器是 en-US。按语言跳转比按国家跳转更符合实际需求。 最终的判断逻辑： const langs = navigator.languages.length ? navigator.languages : [navigator.language]; const preferred = langs[0].toLowerCase(); if (preferred.startsWith("fr")) { location.replace("/fr/"); } else if (!preferred.startsWith("zh")) { location.replace("/en/"); } 中文不跳转，因为中文就在根路径 /。

桌游程序的边界：MachiKoro 的购买流程、索引与 AI

项目代码：https://github.com/yicongl1/Machikoro 规则写对只是第一步。真正让人崩溃的是边界：买不起怎么办、卡槽编号在购买后变了、AI 选了一个不合法的动作、输入的字符串看起来对但匹配不上。 这篇记录 MachiKoro 项目里购买与输入处理的设计，以及修过的几类典型 bug。 购买流程：返回值到底表示什么 早期版本的 player_input() 返回一个 int，这个 int 有时候表示"卡槽编号"，有时候表示"剩余金币数"，还可能是 -1 表示不买。结果就是： 买地标时把金币数当成下标，越界 slot[0] 永远买不到 先扣钱、后校验，买不起也能把金币扣成负数 后来把返回值语义固定下来： enum PurchaseCode { NO_PURCHASE = -1, // 选择 no，结束购买 YELLOW_PURCHASE = -2 // 已成功购买一张大型建筑 }; 普通建筑返回真实的卡槽下标，两个特殊值负责"不买"和"已买地标"。调用方只需要判断这三种情况，不再猜数字的含义。 更好的写法是 enum class + std::optional<int>(C++17 起),避免负数和下标混在一起。但在一个 C++14 的控制台作业里,能用枚举把语义写清楚,已经比"魔法数字"好很多。 先校验，后扣钱 购买普通建筑时，所有失败条件都必须在 withdraw() 之前检查： bool Game::buy_slot(int index) { if (index < 0 || index >= (int)slot.size() || slot[index].empty()) return false; Card* card = slot[index].back(); // 紫卡不能重复拥有 if (card->get_color() == Color::purple) { for (PurpleCard* owned : p->purple_cards) { if (owned->get_name() == card->get_name()) return false; } } // 钱不够 if (p->bank->get_coins() < card->get_cost()) return false; // 到这里才真正扣钱 p->bank->withdraw(card->get_cost()); // ... } 这是一条很朴素的规则：任何可能失败的操作，都把失败判断放在状态修改之前。一旦顺序反了，后面每一条错误分支都要负责"把钱加回去"，很容易漏。
