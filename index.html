给简历写一个生成器：从主页数据到 A4 PDF

每次投申请，简历都要改一遍：这个岗位多放两个项目，那个项目砍掉一段经历；中文版、英文版、法文版各改一次。主页上的数据明明是现成的，简历却要手工维护，时间一长两边就对不上。 于是有了 /cv/：一个只给自己用的简历生成器。左边勾选语言和条目，右边实时预览 A4 纸面，点一下直接下载 PDF。这篇文章记录它是怎么搭起来的，以及中间踩到的几个坑。 一、数据从哪来 站点的首页本身是数据驱动的：教育、实习、项目、竞赛、技能、链接分别放在 data/<lang>/sections/*.yaml 里，Toha 主题负责渲染。简历生成器没有另起一套数据，而是在构建时把三种语言的这些 YAML 直接嵌进页面： {{- $langs := slice "zh-cn" "en" "fr" -}} {{- $cvData := dict -}} {{- range $lang := $langs -}} {{- $entry := dict -}} {{- $d := index site.Data $lang -}} {{- $sec := $d.sections -}} {{- range $key := slice "about" "education" "experiences" "projects" "competitions" "achievements" "skills" "connect" -}} {{- $entry = merge $entry (dict $key (index $sec $key | default (dict))) -}} {{- end -}} {{- $cvData = merge $cvData (dict $lang $entry) -}} {{- end -}} 这样只有一处真相：主页改了什么，简历里就有什么。三个语言版本也天然一致，不需要各自维护。 二、一个不显眼的坑：script 标签里的 JS 上下文 第一版把所有数据渲染进 <script type="application/json">，结果页面里的 JSON 完全解析不了，打开看是这样一个东西： "{\"en\":{\"about\":{\"badges\":[...]" 整段 JSON 被多包了一层引号，里面的引号全被转义了。原因不在 jsonify，而在 Go 模板的上下文感知转义：模板引擎看到输出位置在 <script> 标签里，会按 JavaScript 字符串字面量的规则来转义，于是把整段 JSON 当成一个字符串，套上引号。 修复只需要一个过滤器： <script id="cv-data" type="application/json">{{ $cvData | jsonify | safeJS }}</script> jsonify 保证输出是合法 JSON，而 JSON 本身就是合法的 JS 字面量；safeJS 告诉模板引擎「这段内容已经是安全的 JS，别再包一层」。这个坑在任何 Hugo 站点里往 <script> 注入 JSON 时都会遇到，值得记一笔。 三、勾选、排序与记忆 左侧面板按板块分组：每个板块可以整组开关、上下移动；组内每个条目也可以单独勾选、排序。状态结构大致是： state = { lang: 'zh-cn', contact: true, avatar: true, style: { size: 'md', font: 'sans', layout: 'single' }, groups: { 'zh-cn': { projects: { enabled: true, selected: [...], order: [...] } } }, groupOrder: {} } 整个对象序列化进 localStorage。数据文件以后新增条目时，旧的选择状态长度对不上，就对该组回退为默认全选——不会因为索引错位丢内容。

    给静态博客接上评论区：giscus、主题同步与三个配色坑

    这个站是 Hugo 生成的纯静态站点，托管在 GitHub Pages 上。没有服务器，也就没有地方存评论。想加评论区，绕不开一个问题：数据放在哪。 最后选了 giscus：评论存在 GitHub Discussions 里，前端只加载一个 iframe。这篇文章记录选型、接入过程，以及真正花时间的部分——让评论区和站点主题看起来像一家人。 一、静态站点为什么不能自己写评论 传统做法是「表单 → 后端 → 数据库」。GitHub Pages 只发文件，没有运行时，这条链路走不通。 可行的路线只剩三类： 第三方托管评论：Disqus、giscus、 utterances。 自建 Serverless 后端：Twikoo、Waline，前端 + 云函数 + 数据库。 不叫评论：邮件、Formspree 之类的留言表单。 Disqus 广告和追踪太多，国内访问也不稳定，先排除。Twikoo/Waline 能匿名留言，但要维护 Vercel、数据库和审核后台，对现在的需求偏重。 giscus 的取舍很明确：访客必须有 GitHub 账号，换来的是零后端、零数据库、无广告，评论天然归档在 Discussions 里。 二、giscus 的最小接入 先准备一个公开仓库专门放评论，例如 yicongl1/site-comments。源码仓库是私有的，不能拿来当评论仓库，否则 giscus 读不到。 步骤只有四步： 新建公开仓库； Settings → Features 勾选 Discussions； 新建分类，例如 Comments（类型选 Announcements 即可，讨论由 giscus App 创建）； 安装 https://github.com/apps/giscus，授权到这个仓库。 然后在 https://giscus.app 填仓库，拿到两个 ID： data-repo-id: "R_kgDO..." data-category-id: "DIC_kwDO..."       SY02：用 R 把概率论与数理统计跑一遍

      SY02 是 UTC 城市工程专业的一门概率论与数理统计课。它不像纯数学课那样只推公式，而是要求把每一个结论都用 R 跑出来：模拟、估计、检验，最后对着输出解释「为什么是这样」。结课之后我把七个 TP（Travaux pratiques，实践课）的代码和笔记重新整理成了一个公开档案：yicongl1/sy02-statistiques-r。 这篇文章不是课程讲义的搬运，而是我自己的一份复盘：从描述统计一路走到假设检验，记录每个 TP 到底在练什么、R 里对应的函数是什么、以及那些当时卡住我的地方。 说明：课程讲义、题目与答案的著作权归授课教师和学校所有，仓库里只保留我自己写的 R 代码和课程提供的数据，不发布任何课件 PDF。 一、为什么值得单独建一个仓库 概率统计最容易「看懂」却「不会用」。公式背得下来，换一组数据就不知道从哪下手。我把 SY02 拆成七个独立的 TP 文件夹，每个文件夹都有一份中法双语的 README，写清四件事： 这一节的学习目标； 每个文件负责什么； 核心公式与它在 R 里的落点； 怎么运行、应该看到什么。 这样做的好处是，半年后回来复习时，不需要重新翻课件，只要打开对应 TP 的 README，就知道当时验证的是哪个结论。 二、仓库结构 SY02/ ├── 01-r-basics/ # R 入门与描述统计 ├── 02-probabilities/ # 概率分布与模拟 ├── 03-estimation/ # 点估计与最大似然 ├── 04-confidence-intervals/ # 置信区间与覆盖率 ├── 05-linear-regression/ # 线性回归与诊断 ├── 06-hypothesis-tests/ # 假设检验与功效 ├── 07-tp7-modification/ # 综合修改练习 └── 08-revisions/quiz/ # 计分测验 七个 TP 加一次测验，基本覆盖了从「把数据看明白」到「对数据下判断」的完整链路。
