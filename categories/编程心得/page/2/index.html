从 KMP 到关键路径：把 36 个数据结构实验串成一张图

经典 Gram–Schmidt 与修正版：同样的公式，误差为什么差十几个数量级

项目仓库：https://github.com/yicongl1/Linear-Algebra-Gram-Schmidt Gram–Schmidt 有两个版本。教科书通常先讲经典版（CGS），再提一句“数值上更推荐修正版（MGS）”，然后继续往下写。但这个“更推荐”到底值多少？在什么矩阵上会出事？出事时误差有多大？ 这个课程项目用 MATLAB 和 C 把两个版本都实现了一遍，然后用病态矩阵和随机矩阵把差异量出来。结论比“MGS 更稳”具体得多。 两个版本只差一个下标 经典版对第 k 个向量一次性减去它在所有已构造正交向量上的投影： u_k = v_k - Σ_{j<k} <v_k, u_j> u_j 修正版把投影拆开，每减一次就更新当前向量： v_k ← v_k - <v_k, u_j> u_j, j = 1..k-1 精确算术下两者完全等价。MATLAB 代码也只差一个字母： % CGS：内积始终用原始列 a(:,i) b(:,i) = b(:,i) - dot(a(:,i), b(:,j)) / dot(b(:,j), b(:,j)) * b(:,j); % MGS：内积用已经更新过的 b(:,i) b(:,i) = b(:,i) - dot(b(:,i), b(:,j)) / dot(b(:,j), b(:,j)) * b(:,j); CGS 的每一次投影都基于“原始向量”，所有投影系数一次性算完；MGS 的每一次投影都基于“被前一次投影修改过的向量”。这个顺序差异，决定了舍入误差会不会被后续步骤放大。 为什么会丢精度 把向量 v_k 投影到已构造的正交基上，本质是在做减法。如果 v_k 与某个 u_j 几乎平行，投影项就非常接近 v_k 本身，两个相近的大数相减会产生严重的相消（cancellation），有效数字大量丢失。

转弯时内外轮到底差多少：电子差速的几何、公式与 PWM 映射

项目仓库：https://github.com/yicongl1/EV-Electronic-Differential 机械差速器存在了一百多年，原因很简单：转弯时外侧车轮走的路更长。如果左右轮被刚性轴锁成同一个转速，轮胎只能一边滚一边蹭。电子差速想做的事，是用两个独立电机复现“内外轮各走各的”，只不过把机械结构换成了控制代码。 这篇只回答一个定量问题：给定轴距、轮距和前轮转角，内外轮到底应该差多少？然后把这个结果和模型小车里的 120/180 占空比对上。 先把几何画出来 把车简化成两轮模型：后轴中心到前轴的距离是轴距 L，左右轮中心距是轮距 B，前轮转角 δ。低速、忽略轮胎侧偏时，车辆绕一个瞬时中心转弯，后轴中心的轨迹半径是： R = L / tan(δ) 内侧后轮的半径是 R - B/2，外侧后轮是 R + B/2。同一时间内，车轮走过的弧长与半径成正比，所以轮速也成正比： v_inner = v · (R - B/2) / R v_outer = v · (R + B/2) / R 两式相除，车速 v 被消掉： v_outer / v_inner = (R + B/2) / (R - B/2) 这个比值只由几何决定。轴距越长、轮距越窄、转角越小，比值越接近 1；反过来，大转角 + 宽轮距会让内外轮差得很明显。 代入模型小车的数字 这台小车的轴距约 L = 0.16 m，轮距约 B = 0.12 m。前轮打到 30°： R = 0.16 / tan(30°) = 0.16 / 0.5774 ≈ 0.277 m R - B/2 = 0.217 m R + B/2 = 0.337 m v_outer / v_inner = 0.337 / 0.217 ≈ 1.55 如果车速是 1 m/s，那么内侧轮约 0.78 m/s，外侧轮约 1.22 m/s。这个差异已经足够明显：用同一个 PWM 驱动两侧，转弯时内侧轮胎一定在拖。

20 Hz 的设定点：PX4 OFFBOARD 的五个坑

项目仓库：https://github.com/yicongl1/Drone-Delivery-2022 2022 年那台配送无人机，飞控是 PX4，上层是 Jetson Nano 上的 ROS。所有“自主”最终都落成一件事：以 20 Hz 的频率，把一个位置设定点发给飞控。这篇把当时踩过的五个坑按顺序写下来，每一个都来自“明明代码没错，但飞机不听话”。 坑一：先切模式，再解锁 OFFBOARD（外部控制）模式要求飞控持续收到来自机载计算机的设定点。如果解锁之后迟迟没有设定点进来，PX4 会认为外部链路不可靠，自动上锁——现象就是“解锁了，但螺旋桨没转起来”，或者刚离地就掉下来。 所以现场流程是固定的： 地面站先发 set_mode 切到 OFFBOARD； send_info_node 立刻开始以 20 Hz 发设定点； 再调用 mavros/cmd/arming 解锁。 官方文档里还有一条：解锁后 5 秒内必须进入 OFFBOARD。我们的流程天然满足，但这条规则决定了顺序不能反。 坑二：设定点一停，模式就掉 OFFBOARD 不是“设一次就一直有效”的状态，而是一个必须持续喂数据的模式。任何一次 1 秒的停顿——cin 等你输入航点、打印日志卡住、SSH 断流——都可能让飞控退出 OFFBOARD，飞机随即进入失控保护。 我们为此专门写了一个 send_info_node：只要飞机不是“已解锁且处于 OFFBOARD”这个状态，就以 20 Hz 持续发布速度设定点。它是一张安全网，代价很低（一个只发消息的节点），但没有它，有一次调试就因为在地面站里多敲了一行命令，飞机在半空掉出了 OFFBOARD。 坑三：设定点不能跳 这是整个项目里最影响观感的一条。向飞控发布一个距离 3 米的目标点，和让设定点每 50 ms 挪 5 厘米，飞控接收到的都是“位置”，但响应完全不同：前者是阶跃输入，姿态会猛冲、过冲、再修正；后者是一条平滑轨迹。 void add_target(int i) { for (int j = 0; j < 3; j++) { if (abs(next_point[j] - fly_point[i + 1][j]) > 0.3) { if (next_point[j] > fly_point[i + 1][j]) { next_point[j] -= change; } else { next_point[j] += change; } } else { next_point[j] = fly_point[i + 1][j]; } } } change 取 0.02~0.05 m。剩下的距离小于 0.3 m 时直接吸附到目标点，否则永远差最后一点点。这个“阈值内吸附”的写法很土，但解决了“逐步逼近永远到不了”的问题。

仿真 90%、实地 80%：一次足球机器人赛的落差清单

项目仓库：https://github.com/yicongl1/iLoboke-Robot-Soccer-2022 技术报告里有一张自评表，是整份文档里最诚实的一页： 指标 通用数据 最好数据 软件仿真进球 50% 90% 软硬件联调 40% 80% 仿真 90%，实地 80%。看起来只差 10 个点，但换个说法就是：每十个点位会有一个踢不进，而比赛只有五个点位、每个 15 秒。这篇文章是把那个 10% 拆开看看。 落差是从哪儿来的 位置是估的，不是量的。 仿真里球有一个确定坐标；实地上只有一个带噪声的估计值，由场地上方摄像头、标定矩阵和球模板共同给出。所有阈值——“球到 5 号 30 以内”“3 号到点 5 以内”——在仿真里是精确判断，在实地是在噪声上做判断。 地毯不吃力学那一套。 仿真里球的减速可以算出来，实地上取决于地毯的毛向、接缝、机器人的吸球口高度。同一脚传球，在地毯这一头能到，挪两米就到不了。 守门员是会动的。 规则写得很清楚：“守门员状态未定、可移动”。也就是说球门后面不是空的，而我们的脚本基本假设了固定球门。7 月 26 日专门为这件事改过一轮。 反馈有延迟。 Lua 每帧跑一次，但“踢出去了”这个事实要等 C++ 侧或视觉侧确认。在这中间的几帧里，状态机看到的是旧世界。 四副补丁，各治一种病 帧确认（Cbuf_cnt(条件, 120)）。 治“抖动”——一次错误判定不该让流程往前走。代价是反应变慢：120 帧的确认窗口意味着每次状态切换至少要等两秒（按 60 帧/秒估）。 传接之间的保障环节。 治“踢空”——传完球不立刻进入射门，而是先确认接球方真的拿到了。这一层里接球方还能继续跑位，时间可调。这是技术报告里评为“效果很好、符合预期”的两项之一。 按球的左右位置镜像跑位。 治“撞车”——一开始把两台机器人的位置写死，结果经常挤在同一个点。后期重写的版本按 CGetBallY() 的正负把接球点镜像到 ±35 / ±148。 传球力度分段。 治“近传过猛、远传不到位”——把固定力度换成按目标距离分档的函数。这是 6 月 27 日改的，也是我认为单点收益最高的一次修改。 四副补丁都有效，但没有一副解决根本问题：它们都是在用代码补偿一个没有被标定的环境。 数据说明了什么 2022 年 9 月 18 日全国预选赛，2 号场地第 1 场，两轮取最优：

把 15 秒的比赛规则写成状态机：Lua 战术层与 C++ 技能层

项目仓库：https://github.com/yicongl1/iLoboke-Robot-Soccer-2022 2022 年那场足球机器人赛，规则里最关键的一句话是：每个固定点位 15 秒内完成，射门前至少一次传接配合。它把“让机器人踢球”这道开放题，压成了一道可以被脚本穷举的流程题——两个演员、五个起点、三个状态。 这篇拆一下当时的代码是怎么组织的：Lua 战术层、C++ 技能层，以及一个我到现在还觉得有意思的 bug。 平台只给两层接口 赛项平台 SOM 3.4.2 的扩展方式很克制，只有两层： Team/lua_scripts/play/Package/<场景>/ 下的 Lua 战术脚本，由 Play.lua 调度； Team/user_skills/<名字>.dll 下的 C++ 技能动态库，Lua 通过 task.KickerTask("名字") 直接调用。 Play.lua 本身就是一个状态机调度器。每个战术脚本用一张表注册进去： gPlayTable.CreatePlay{ name = "P_Back", firstState = "GetBall", ["GetBall"] = { switch = ..., Kicker = ..., Receiver = ... }, } 每帧做三件事：换了 play 就重置到 firstState；调当前状态的 switch() 拿到下一个状态名（或 "finish"）；对状态里列出的每个角色执行对应的 task()。task 是闭包，最终落到 C++ 侧的 CKicker_Skill(name, posX, posY, dir, kickflat, kp, cp)——name 就是 DLL 的文件名，kp 和 cp 是平射与挑射的力度，不写就是 kp=127、cp=6。
