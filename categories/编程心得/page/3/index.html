    项目代码与报告：https://github.com/yicongl1/MPPT-direct MPPT 算法本身只是“决定往哪走”，真正执行的是 DC-DC 变换器。这篇讲两件事：为什么 BA04 项目选了 SEPIC，以及报告里四种算法各自的假设和代价。 变换器在 MPPT 里到底做什么 光伏组件的输出阻抗随辐照度、温度变化。MPPT 控制器改变变换器的占空比 d，等价于改变组件看到的等效负载，从而把工作点推到 MPP。 所以变换器不是“可选的外围电路”，它决定了： 工作点能不能覆盖到 MPP（输入电压范围）； 占空比变化对工作点的影响有多灵敏； 输出电压的极性和范围能不能接后级。 五种拓扑的取舍 拓扑 电压关系 输出极性 特点 Buck 只能降压 同相 简单、效率高；输入电压必须始终高于输出 Boost 只能升压 同相 简单；输入电压必须始终低于输出 Buck-Boost 可升可降 反相 范围宽；输出是负压，后级要处理 Cuk 可升可降 反相 输入输出电流都连续；同样是负压 SEPIC 可升可降 同相 范围宽、极性友好；器件比 Buck/Boost 多 光伏的麻烦在于输入电压大幅波动：辐照度低时组件电压下降，温度高时电压也下降。如果固定一个输出电压： 用 Buck，低辐照时输入可能低于输出，占空比顶到 1 也追不上； 用 Boost，高辐照时输入可能高于输出，根本没法工作； 用 Buck-Boost 或 Cuk，范围够了，但输出反相，后级需要额外处理； 用 SEPIC，既能升也能降，输出还与输入同相。 这就是项目选 SEPIC 的直接原因：宽输入范围 + 同相输出。代价是多了两个电感、两个电容和一个开关管，损耗和体积都上去了。 SEPIC 的两个阶段 SEPIC 的工作可以粗略分成两段： 开关导通：输入电感 L1 直接跨在输入上储能；耦合电容 C1 通过第二个电感 L2 放电，L2 也储能；二极管截止，负载由输出电容供电。 开关关断：L1 和 L2 的电流经二极管流向输出，同时给 C1 充电；负载得到能量。 理想情况下，输出电压与占空比的关系是：

        光伏的 MPP 与 P&O：为什么扰动、为什么振荡、改进在哪里

        项目代码与报告：https://github.com/yicongl1/MPPT-direct 这是 UTC BA04 课程项目里我负责的部分：P&O（扰动观察法）和它的改进版 P&OA。这篇不铺开讲四种算法，只把 P&O 这条线讲清楚——它为什么成立、代价是什么、改进到底改在哪，以及为什么我们跑完整整一年，两种算法的发电量只差 0.5%。 为什么会有“最大功率点” 光伏组件把光直接变成直流电。对任意时刻，输出功率就是电压乘电流： P = V · I 但 I-V 曲线不是一条直线。电压从 0 升到开路电压的过程中，电流先基本平坦、再快速下降，功率则先升后降，只有一个峰值——这就是 MPP（最大功率点）。 麻烦在于它的位置不固定： 辐照度升高，整条曲线向右上方移动，MPP 功率变大； 温度升高，电压下降，曲线向左移动，MPP 功率变小； 云、遮挡、组件老化，都会让曲线变形。 如果负载把工作点钉在某个固定电压上，组件大部分时间都不在 MPP，损失可以到 20~30%。MPPT 要做的事，就是让工作点一直跟着 MPP 跑。 直接法与间接法 课程报告把方法分成两类： 直接法：直接改变组件电压（或 DC-DC 的占空比），测量由此产生的功率变化，再决定下一步。P&O、INC 都属于这一类。它不依赖组件参数，对老化、遮挡、辐照度突变适应性强；代价是会一直在 MPP 附近“试探”。 间接法：不主动扰动，用模型或可测量推算 MPP，比如开路电压比例系数、短路电流比例系数、查表、曲线拟合。实现简单、稳态不振荡；但系数要逐块标定，环境突变时偏差大。 我们做的是直接法。原因很实际：手里有一整年的实测数据，组件参数随温度、老化变化，直接法更容易在仿真里复现真实工况。 P&O 的判据只有一句话 P&O 的逻辑朴素到可以用三行写完： P(k) = V(k) · I(k) if P(k) > P(k-1): 保持原来的扰动方向 else: 反向 也就是：功率在涨，就继续往这个方向推；功率在跌，说明推过头了，往回走。作用在 SEPIC 上时，被扰动的量是占空比 d： d(k+1) = d(k) + step · direction 它只需要测量电压和电流，不需要知道组件型号、辐照度或温度，这是它最大的优点。

          静态站的语言跳转：为什么我没用 IP 定位

          站点有中文、英文、法文三个版本。之前的做法是让访客自己点右上角的语言选择器；最近加了一个“首次访问自动跳转”，规则很简单： 浏览器语言是法语 → /fr/ 浏览器语言是中文 → 中文首页 其他语言 → /en/ 没有采集 IP，也没有调用任何第三方接口。 这篇记录为什么这么做，以及静态站做语言跳转时容易踩的坑。 静态站拿不到 IP 这是最先要接受的事实。GitHub Pages 这类纯静态托管只负责把文件发出去，不执行服务端代码，所以： 不能在服务器端读 X-Forwarded-For 不能根据国家做 302 不能在 HTML 返回前决定语言 想在浏览器里按国家跳转，只能调用第三方 IP 地理库： const res = await fetch("https://ipwho.is/"); const { country_code } = await res.json(); 这能工作，但代价不小： 多一次外部请求：首屏要等它返回，慢的时候会先看到中文再跳走。 隐私问题：IP 属于个人数据。站点在法国，面向欧洲访客时，把每个访客的 IP 发给第三方需要更谨慎地说明处理目的。 误判：VPN、公司出口 IP、跨境网络都会让“国家”不等于“语言”。 可用性：免费接口有限流，挂掉时只能回退。 对个人作品集来说，这些成本换来的精度并不值得。 浏览器语言是更直接的信号 访客想要什么语言，浏览器其实已经说了： navigator.language // "fr-FR" navigator.languages // ["fr-FR", "fr", "en"] 它比 IP 更接近“用户能读什么语言”，而不是“用户此刻在哪”。一个法国人在德国出差，浏览器仍然是 fr-FR；一个在法国的英语使用者，浏览器是 en-US。按语言跳转比按国家跳转更符合实际需求。 最终的判断逻辑： const langs = navigator.languages.length ? navigator.languages : [navigator.language]; const preferred = langs[0].toLowerCase(); if (preferred.startsWith("fr")) { location.replace("/fr/"); } else if (!preferred.startsWith("zh")) { location.replace("/en/"); } 中文不跳转，因为中文就在根路径 /。

                  这两天给站点加学业档案，踩了两个坑。都不是什么高深问题，但都属于“本地一切正常、线上就是不对”的那类，值得记一下。 一、为什么线上和本地预览不一样 现象 推送之后打开线上页面：导航栏是新的，说明 HTML 已经更新；但新加的内容完全没有样式——卡片没有边框，校徽按 SVG 原始尺寸铺满半屏。 本地 localhost 预览却完全正常。 排查 先确认服务器上的文件： git cat-file -s "origin/main:css/site.css" # 发布提交里的文件大小 有，大小也对。再看线上页面引用了什么： <link rel="stylesheet" href="/application.<hash>.css"> <link rel="stylesheet" href="/css/site.css"> 关键就在这两行的区别： application.<hash>.css 是主题打包的，文件名带内容哈希，每次构建都会变 /css/site.css 是我自己加的补丁样式，文件名永远不变 浏览器缓存的是后者。它可能还存着几次部署以前的版本，那时候还没有新加的那些 class。于是新 HTML 配上旧 CSS，结构在、样式没了。 本地预览没有这层缓存，所以永远正常。 解决 让 URL 跟着内容走。在 Hugo 模板里算文件内容的 MD5： {{ $siteCssHash := md5 (os.ReadFile "static/css/site.css") }} <link rel="stylesheet" href="{{ "/css/site.css" | relURL }}?v={{ $siteCssHash }}" /> 输出： <link rel="stylesheet" href="/css/site.css?v=f92eac970bd1dfa87e9f47bf5e30cbf6"> 内容变，URL 就变；内容不变，缓存继续有效。比 ?v=时间戳 好：时间戳会让每次构建都强制重新下载，白白浪费。 一个容易误判的细节 排查时我一度以为线上 CSS 少了内容： $r.Content.Length # 8884 而本地文件是 9942 字节。差了五百多。 其实 Content.Length 数的是字符，文件大小是字节。中文在 UTF-8 里一个字符占三个字节。把 Content 按 UTF-8 写回文件，正好 9472 字节，和发布版本完全一致。
