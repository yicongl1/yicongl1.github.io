从课程作业到可维护项目：MachiKoro 的重构与归档

项目代码：https://github.com/yicongl1/Machikoro MachiKoro 最初是上海大学 2022 秋季「算法与编程」的课程项目。第一版能跑，但结构很粗糙；后来花了一轮时间做重构、补文档、留归档，才变成现在这个可以拿给别人看的样子。 这篇不谈具体规则，只谈“一个课程作业怎么收尾”。 第一版的问题 旧版原型还留在仓库的 archive/legacy-v0.1/ 里。它有几个典型问题： Game 同时负责规则、界面和输入，一个文件几千行 购买流程用 int 返回“金币数或卡槽号”，语义靠猜 卡牌、玩家对象全部 new 出来，没有释放 输入混用 cin >> 和 getline()，偶尔读到空行 洗牌用 random_shuffle，随机源不可控 基类没有虚析构函数 这些问题在“能演示”的阶段都不致命，但一旦要改规则，就会一个接一个冒出来。 重构做了什么 不是重写，而是按风险从高到低逐个处理： 先修正确性：购买先校验后扣钱、紫卡重复判断、卡槽越界、紫卡触发条件、购物中心下标、体育场不向自己收钱。 再修输入：统一 getline()，加 normalize()、parse_int()、EOF 处理。 然后修资源与未定义行为：Card 加虚析构、成员默认初始化、random_shuffle 换成 std::shuffle + std::mt19937。 最后整理结构：把购买流程的返回值改成 PurchaseCode，把 AI 的决策收敛成“合法候选集”，把重复的打印逻辑抽成函数。 每一步都保持“改完能编译、能跑一局”。课程项目没有测试框架，最怕的是一次改太多，最后不知道是哪一处改坏了。 为什么保留旧版和课程笔记 仓库里现在有几类“看起来没用”的东西： archive/legacy-v0.1/：第一版源码 archive/course-notes/课程笔记.docx：原始课程笔记 docs/course-notes.md：整理后的 Markdown 笔记 docs/uml/：类图（Visio 源文件 + PDF） docs/demo/：三段演示视频 它们不参与编译，但回答了几个以后一定会被问到的问题： 这个项目是怎么一步步变成现在这样的？ 当时的设计意图是什么？ 它真的能跑吗？ 尤其是 UML。写代码的时候觉得类图是形式主义，等过几个月再回来看，类图比代码更快让人恢复上下文。 如果重做，我会怎么改 1. 拆开 Game / View / Controller 现在 Game 既算钱又打印菜单，还解析输入。理想的结构是：

桌游程序的边界：MachiKoro 的购买流程、索引与 AI

项目代码：https://github.com/yicongl1/Machikoro 规则写对只是第一步。真正让人崩溃的是边界：买不起怎么办、卡槽编号在购买后变了、AI 选了一个不合法的动作、输入的字符串看起来对但匹配不上。 这篇记录 MachiKoro 项目里购买与输入处理的设计，以及修过的几类典型 bug。 购买流程：返回值到底表示什么 早期版本的 player_input() 返回一个 int，这个 int 有时候表示“卡槽编号”，有时候表示“剩余金币数”，还可能是 -1 表示不买。结果就是： 买地标时把金币数当成下标，越界 slot[0] 永远买不到 先扣钱、后校验，买不起也能把金币扣成负数 后来把返回值语义固定下来： enum PurchaseCode { NO_PURCHASE = -1, // 选择 no，结束购买 YELLOW_PURCHASE = -2 // 已成功购买一张大型建筑 }; 普通建筑返回真实的卡槽下标，两个特殊值负责“不买”和“已买地标”。调用方只需要判断这三种情况，不再猜数字的含义。 更好的写法是 enum class + std::optional<int>（C++17 起），避免负数和下标混在一起。但在一个 C++14 的控制台作业里，能用枚举把语义写清楚，已经比“魔法数字”好很多。 先校验，后扣钱 购买普通建筑时，所有失败条件都必须在 withdraw() 之前检查： bool Game::buy_slot(int index) { if (index < 0 || index >= (int)slot.size() || slot[index].empty()) return false; Card* card = slot[index].back(); // 紫卡不能重复拥有 if (card->get_color() == Color::purple) { for (PurpleCard* owned : p->purple_cards) { if (owned->get_name() == card->get_name()) return false; } } // 钱不够 if (p->bank->get_coins() < card->get_cost()) return false; // 到这里才真正扣钱 p->bank->withdraw(card->get_cost()); // ... } 这是一条很朴素的规则：任何可能失败的操作，都把失败判断放在状态修改之前。一旦顺序反了，后面每一条错误分支都要负责“把钱加回去”，很容易漏。

用 C++ 给桌游建模：MachiKoro 的卡牌体系与多态结算

项目代码：https://github.com/yicongl1/Machikoro MachiKoro（街角小吃店）是个很适合练面向对象的题目：规则不算复杂，但卡牌类型多、触发时机分散，而且每一种卡的效果都不一样。用 if/else 硬写当然能跑，但很快就会变成一坨难以维护的分支。 这篇记录我们怎么把规则拆成对象，以及事后回看时觉得哪里还能更好。 规则先拆成“谁在什么时候做什么” 一个回合可以简化成： 掷骰 → 收入结算（红 → 蓝/绿 → 紫）→ 建造 1 张建筑 红卡：其他玩家付钱给卡主（咖啡馆、家庭餐厅） 蓝卡：所有拥有该卡的玩家收钱（麦田、牧场、森林、矿场、苹果园） 绿卡：当前玩家收钱，部分卡按图标数量加倍（面包店、奶酪工厂等） 紫卡：当前玩家对其他人收钱或交换（体育场、电视台、商业中心） 黄卡：四座地标，改变规则本身（火车站、商业中心、游乐园、广播塔） 结算顺序不是随便定的：红卡要在蓝卡之前，因为红卡会先把钱从别人手里拿走；紫卡放在最后，因为它可能改变手牌或金币。规则里的顺序就是代码里的调用顺序。 一个基类，五种颜色 所有卡共有的东西放进 Card：名字、价格、收益、点数区间、图标、颜色。 class Card { public: virtual ~Card() = default; virtual void action(Bank *p1, Bank *p2, Card *c1, Card *c2, int val) = 0; void set_card(string name, int cost, int value, int low_roll, int high_roll, Icon icon, Color color); int get_value(); int get_cost(); Color get_color(); Icon get_icon(); int get_low_roll(); int get_high_roll(); // ... private: int low_roll = 0; int high_roll = 0; int cost = 0; int value = 0; Color color = Color::blue; Icon icon = Icon::none; string name; }; action() 是纯虚函数，五种子类各自实现。新增一张卡，只需要写一个构造函数和（必要时）一个 action()，主流程不用动。

【网站搭建】静态资源的缓存与多语言链接

这两天给站点加学业档案，踩了两个坑。都不是什么高深问题，但都属于“本地一切正常、线上就是不对”的那类，值得记一下。 一、为什么线上和本地预览不一样 现象 推送之后打开线上页面：导航栏是新的，说明 HTML 已经更新；但新加的内容完全没有样式——卡片没有边框，校徽按 SVG 原始尺寸铺满半屏。 本地 localhost 预览却完全正常。 排查 先确认服务器上的文件： git cat-file -s "origin/main:css/site.css" # 发布提交里的文件大小 有，大小也对。再看线上页面引用了什么： <link rel="stylesheet" href="/application.<hash>.css"> <link rel="stylesheet" href="/css/site.css"> 关键就在这两行的区别： application.<hash>.css 是主题打包的，文件名带内容哈希，每次构建都会变 /css/site.css 是我自己加的补丁样式，文件名永远不变 浏览器缓存的是后者。它可能还存着几次部署以前的版本，那时候还没有新加的那些 class。于是新 HTML 配上旧 CSS，结构在、样式没了。 本地预览没有这层缓存，所以永远正常。 解决 让 URL 跟着内容走。在 Hugo 模板里算文件内容的 MD5： {{ $siteCssHash := md5 (os.ReadFile "static/css/site.css") }} <link rel="stylesheet" href="{{ "/css/site.css" | relURL }}?v={{ $siteCssHash }}" /> 输出： <link rel="stylesheet" href="/css/site.css?v=f92eac970bd1dfa87e9f47bf5e30cbf6"> 内容变，URL 就变；内容不变，缓存继续有效。比 ?v=时间戳 好：时间戳会让每次构建都强制重新下载，白白浪费。 一个容易误判的细节 排查时我一度以为线上 CSS 少了内容： $r.Content.Length # 8884 而本地文件是 9942 字节。差了五百多。 其实 Content.Length 数的是字符，文件大小是字节。中文在 UTF-8 里一个字符占三个字节。把 Content 按 UTF-8 写回文件，正好 9472 字节，和发布版本完全一致。

在 UNIX 课上写 Shell：sed、awk 与一个文件同步器

LO03 是我第一次系统地用 UNIX。课分三块：Linux、Unix、系统，前面讲内存、进程、文件系统，后面全是命令行和脚本。每周的 TD 不是选择题，而是给你一个文件、一个需求，让你用 sed、awk、grep 把它做出来。 这门课最直接的影响，是我后来在 Linux 上排错时不再怕终端了。但它的作业也让我第一次意识到：Shell 写起来很快，写对很难。 从「一切皆文件」开始 课程的第一句话是 « tout est fichier »——所有东西都可以通过文件访问。用户信息在 /etc/passwd，密码哈希在 /etc/shadow，日志在 /var/log，设备在 /dev。理解了这一点，后面的大量操作就变成了「读一个文件、改一个文件」。 内存那一部分讲分页、MMU、页面替换（FIFO、LRU、时钟算法），进程那一部分讲 PCB、临界区、信号量。这些概念后来在别的地方反复出现，但当时最让我头疼的，还是每周的脚本作业。 几个当时写的脚本 1. 从名单批量建账号 题目给一个文本文件，每行两个名字，要求生成登录名、批量创建用户。当时的写法大概是这样： #!/bin/bash if [ $# -ne 1 ]; then echo "Usage : $0 fichier" exit 0 fi if [ ! -r "$1" ]; then echo "Fichier <$1> inexistant" exit 0 fi uid=1000 sed '/^#/d' "$1" | while read w1 w2 do ini1=$(echo "$w1" | cut -c1,2 | tr '[A-Z]' '[a-z]') ini2=$(echo "$w2" | cut -c1,2 | tr '[A-Z]' '[a-z]') login="$ini1$ini2" useradd -c "$w2 $w1 - TP ADMIN LINUX" \ -d "/home/$login" -u "$uid" -s /bin/bash "$login" ((uid++)) done 它用到了 $#（参数个数）、$1（第一个参数）、test -r（可读）、sed 删注释行、cut 取前两个字母、tr 转小写。现在看，这段代码问题不少：
