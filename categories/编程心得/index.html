      项目仓库：https://github.com/yicongl1/TN09-BEST-Territorial-Well-Being BEST 项目要回答的问题很宏大：一个领土系统怎样才算“均衡”？但落到研究助理的日常，它先变成三个更小的问题： 领土系统由哪些部分构成？ 福祉由哪些维度构成？ 均衡用什么来观测？ 这三个问题各自需要一套文献综述，最后还要落到可以计算的指标上。这篇记录我在 TN09 里做这三步的方法，以及最后得到的两套指标表。 先做三份综述，而不是一份大综述 “领土系统”“福祉”“均衡”看起来属于同一个话题，但它们的文献传统完全不同：城市动力学、福祉经济学、区域规划、公共政策各自有一套词汇。如果混在一个检索式里，结果会被数量最多的领域淹没。 所以我把它们拆成三份独立的 PRISMA 综述： 主题 分析篇数 主要问题 领土系统 360 领土如何组织？在哪些尺度上？ 福祉 120 居民福祉由哪些维度构成？ 领土均衡 80 哪些杠杆能带来协调发展？ PRISMA 的流程本身不复杂： 识别研究 → 去重 → 标题/摘要筛选 → 全文阅读 → 纳入/排除 难的是保持一致：同一篇文章在不同阶段被不同标准判断，最后就会得到不可复现的语料。我用了三样东西来控制： 一套固定的检索式与数据库（Scopus、Google Scholar、HAL、PROSPERO）； 一张纳入/排除表，每篇文章记录“相关 / 部分相关 / 不相关”及理由； Zotero 管理引用、注释和交叉引用。 最后得到 560 篇的语料。这个数字不是成果本身，真正的成果是：每篇文章都能追溯为什么被纳入。 把概念变成指标 综述回答“概念是什么”，指标回答“怎么观测”。两者之间需要一次翻译。 领土系统：134 项可持续指标 Agenda 21 提供了 134 项城市可持续指标。我把它们按四个维度分类： 经济：生产率、增长、消费、基础设施、交通、住房； 社会：人口、教育、健康、贫困； 环境：水、空气、土地、生态； 制度：治理、参与、规划能力。 然后补充法国本地数据源（INSEE、ADEME、eaufrance、ATMO France、部委），把“概念指标”变成“可采集指标”。 福祉：OECD Better Life Index 的 11 个维度 福祉更容易被当成一个主观词。OECD 的 Better Life Index 把它拆成 11 个维度：

          整改项为什么会失效：从「通用整改项」到 OPR 复核

          项目仓库：https://github.com/yicongl1/TN10-MOEX-OPC-Portfolio 在施工管理里，整改项（réserve）看起来只是一条记录：哪里有问题、谁去改、改完打勾。真正进入 OPR（竣工验收准备）阶段后，问题会变得很具体：同样的缺陷在几十个办公隔间里重复出现，记录数量迅速上升，而复核的人手没有增加。 这篇拆一下我在 TN10 实习里观察到的核心矛盾：录入越省事，复核越费事。以及为什么“定位”不是一个可选的细节，而是整改项能不能成立的前提。 一条整改项至少要回答五个问题 一条可执行的整改项，必须能让人在不问你的情况下采取行动： 在哪里：楼层、区域、图纸、参照点； 是什么：足够明确的技术描述； 谁负责：专业分包与施工单位； 何时完成：期限或截止日期； 证据：照片、状态历史、验收记录。 少任何一项，现场就会开始“找人、解释、补照片、重新确认”。在重复性办公空间里，这种沟通成本会被数量放大。 通用整改项：省了录入，丢了定位 为了减少录入，常见做法是把多个同类问题合并成一条 “通用整改项”（réserve générale）： “34–39 层所有缺少喷淋装饰圈的点位，请统一整改。” 纸面上看，一条记录覆盖了几十个点，效率很高。现场却会出现三个问题： 施工单位处理了一部分，忘了另一部分； MOE 不知道最初到底有多少个点，无法判断是否全部闭合； 整改项没有精确位置，复核只能靠“再巡一遍”。 于是，录入节省的时间被转移到复核、催办和争议处理上。最坏的情况是：记录显示“已整改”，现场仍然有缺失，但没有人能证明漏了哪几个点。 定位不是录入细节，而是控制手段。 没有位置，就没有可验证的完成标准。 把整改项做成结构化数据 在 TN10 里，我用 IDCapture 把现场问题结构化成一张可跟踪的工单： 位置：楼层、区域、图纸/点位； 专业包（lot）与施工单位； 技术描述； 期限或截止日期； 照片； 状态：待整改 / 企业已整改 / MOE 已验收 / 有争议 / 拒绝。 这套结构的关键不是“字段多”，而是每个字段都对应一个动作： 位置决定施工单位能不能找到； 专业包决定找谁； 期限决定什么时候催； 状态决定这条记录有没有真正闭合； 照片决定争议时谁有证据。 统计也围绕这些字段做：按企业看问题集中度，按楼层/区域看返工组织，按时间看 OPR 的整改与验收节奏。统计的目的不是做报表，而是决定下一周把精力放在哪里。 三个容易忽略的现场细节 1. 状态不等于完成 “企业已整改”和“MOE 已验收”是两件事。很多项目只统计前者，导致“完成率”看起来很好，但现场仍有大量未复核的点。真正应该盯的是已验收关闭的数量。 2. 通用项要拆回点位 如果业务上必须使用通用整改项，至少要保留每个发生点的定位，或者要求施工单位按点位回报。否则“通用”会变成“到处都有，等于哪里都没有”。 3. 工具落地比工具本身难 账号、角色、图纸切分、session、三级校验流程、培训，任何一项没做好，工具就会退化成“存照片的地方”。在 TN10 里，工具落地本身就是一项独立工作，不是 IT 部门配好就能用。

            从 KMP 到关键路径：把 36 个数据结构实验串成一张图

            项目仓库：https://gitee.com/yicongl1/data-structures-cpp 数据结构课的内容很容易学成散点：线性表、栈、队列、串、树、图，每一章都有一堆算法。真正有用的时刻，是你能把它们连起来——知道 KMP 的失效函数和树的递归、图的拓扑排序共享同一种“用结构换时间”的思路。 这份仓库把第 3–7 章整理成 36 个专题模块，每个模块一个头文件加一个可运行的 Test*.cpp。这篇挑三个点，串一下从串到图的路径。 KMP：失效函数到底在记什么 朴素匹配在失配时把模式串整体右移一位，KMP 则利用“已经匹配过的前缀”直接跳到下一个可能的位置。核心是失效函数 f[]： void GetFailure(const String &pat, int f[]) { f[0] = -1; int j = 0, k = -1; while (j < pat.GetLength() - 1) { if (k == -1 || pat[k] == pat[j]) f[++j] = ++k; else k = f[k]; } } f[j] 的含义是：pat[0..j-1] 的最长相等真前缀与真后缀的长度。匹配失败时，j = f[j] 把模式串向右滑到“已经匹配的后缀还能继续用”的位置，而不是从头再来。 匹配循环： while (i < ob.GetLength() && j < pat.GetLength() && pat.GetLength() - j <= ob.GetLength() - i) { if (j == -1 || pat[j] == ob[i]) { i++; j++; } else j = f[j]; } 最后一个条件 pat.GetLength() - j <= ob.GetLength() - i 是提前退出：目标串剩下的长度已经不够模式串，没必要再比。时间复杂度 O(n + m)，空间 O(m)。

                  项目仓库：https://github.com/yicongl1/Linear-Algebra-Gram-Schmidt Gram–Schmidt 有两个版本。教科书通常先讲经典版（CGS），再提一句“数值上更推荐修正版（MGS）”，然后继续往下写。但这个“更推荐”到底值多少？在什么矩阵上会出事？出事时误差有多大？ 这个课程项目用 MATLAB 和 C 把两个版本都实现了一遍，然后用病态矩阵和随机矩阵把差异量出来。结论比“MGS 更稳”具体得多。 两个版本只差一个下标 经典版对第 k 个向量一次性减去它在所有已构造正交向量上的投影： u_k = v_k - Σ_{j<k} <v_k, u_j> u_j 修正版把投影拆开，每减一次就更新当前向量： v_k ← v_k - <v_k, u_j> u_j, j = 1..k-1 精确算术下两者完全等价。MATLAB 代码也只差一个字母： % CGS：内积始终用原始列 a(:,i) b(:,i) = b(:,i) - dot(a(:,i), b(:,j)) / dot(b(:,j), b(:,j)) * b(:,j); % MGS：内积用已经更新过的 b(:,i) b(:,i) = b(:,i) - dot(b(:,i), b(:,j)) / dot(b(:,j), b(:,j)) * b(:,j); CGS 的每一次投影都基于“原始向量”，所有投影系数一次性算完；MGS 的每一次投影都基于“被前一次投影修改过的向量”。这个顺序差异，决定了舍入误差会不会被后续步骤放大。 为什么会丢精度 把向量 v_k 投影到已构造的正交基上，本质是在做减法。如果 v_k 与某个 u_j 几乎平行，投影项就非常接近 v_k 本身，两个相近的大数相减会产生严重的相消（cancellation），有效数字大量丢失。

                      转弯时内外轮到底差多少：电子差速的几何、公式与 PWM 映射

                      项目仓库：https://github.com/yicongl1/EV-Electronic-Differential 机械差速器存在了一百多年，原因很简单：转弯时外侧车轮走的路更长。如果左右轮被刚性轴锁成同一个转速，轮胎只能一边滚一边蹭。电子差速想做的事，是用两个独立电机复现“内外轮各走各的”，只不过把机械结构换成了控制代码。 这篇只回答一个定量问题：给定轴距、轮距和前轮转角，内外轮到底应该差多少？然后把这个结果和模型小车里的 120/180 占空比对上。 先把几何画出来 把车简化成两轮模型：后轴中心到前轴的距离是轴距 L，左右轮中心距是轮距 B，前轮转角 δ。低速、忽略轮胎侧偏时，车辆绕一个瞬时中心转弯，后轴中心的轨迹半径是： R = L / tan(δ) 内侧后轮的半径是 R - B/2，外侧后轮是 R + B/2。同一时间内，车轮走过的弧长与半径成正比，所以轮速也成正比： v_inner = v · (R - B/2) / R v_outer = v · (R + B/2) / R 两式相除，车速 v 被消掉： v_outer / v_inner = (R + B/2) / (R - B/2) 这个比值只由几何决定。轴距越长、轮距越窄、转角越小，比值越接近 1；反过来，大转角 + 宽轮距会让内外轮差得很明显。 代入模型小车的数字 这台小车的轴距约 L = 0.16 m，轮距约 B = 0.12 m。前轮打到 30°： R = 0.16 / tan(30°) = 0.16 / 0.5774 ≈ 0.277 m R - B/2 = 0.217 m R + B/2 = 0.337 m v_outer / v_inner = 0.337 / 0.217 ≈ 1.55 如果车速是 1 m/s，那么内侧轮约 0.78 m/s，外侧轮约 1.22 m/s。这个差异已经足够明显：用同一个 PWM 驱动两侧，转弯时内侧轮胎一定在拖。
